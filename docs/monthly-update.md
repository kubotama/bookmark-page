# 月次依存パッケージ更新手順

## 目的

Dependabot による依存パッケージの更新と、Node.js のバージョン管理を定期的に確認し、アプリケーションの安全性・安定性・保守性を維持する。

通常の更新作業は月に1回程度まとめて実施する。ただし、セキュリティ上の問題や緊急性の高い更新は、月次作業を待たずに対応する。

## 0. 作業用のブランチの作成

```bash
git switch main
git pull --ff-only
git switch -c chore/monthly-dependency-updates-2026-10
```

## 1. Dependabot alerts の確認

1. [Dependabot alerts](https://github.com/kubotama/bookmark-page/security/dependabot) を開く。
2. 未解決のセキュリティアラートがないか確認する。
3. アラートがある場合は、影響を受けるパッケージ、脆弱性の深刻度、修正版の有無を確認する。
4. 修正用 PR が作成されている場合は、通常の更新 PR より優先して対応する。
5. 修正をマージした後、アラートが `Fixed` になっていることを確認する。

修正用 PR がない場合は、手動で更新する必要があるか調査する。

## 2. Dependabot の更新 PR の確認

1. [Pull requests](https://github.com/kubotama/bookmark-page/pulls) を開く。
2. 未マージの Dependabot PR を確認する。
3. 更新対象のパッケージ、変更前後のバージョン、リリースノートを確認する。
4. PR の Checks で CI の実行結果を確認する。

更新の種類に応じて、次の点に注意する。

- **パッチ更新**：修正内容を確認し、CI が成功していればマージを検討する。
- **マイナー更新**：新機能、非推奨機能、関連パッケージとの互換性を確認する。
- **メジャー更新**：破壊的変更、移行手順、実行環境の要件を確認する。
- **セキュリティ更新**：脆弱性と修正内容を確認し、優先して対応する。

複数のパッケージが1つの PR にまとめられている場合は、更新対象を把握してからマージする。

## 3. 除外しているメジャー更新の確認

現在の `.github/dependabot.yml` では、次のパッケージのメジャー更新を除外している。

- `eslint*`
- `@eslint*`
- `typescript-eslint`

これらは通常の Dependabot 更新 PR だけでは更新の必要性を判断できないため、月に1回程度、手動で確認する。

### 3.1 現在のバージョンを確認する

リポジトリのルートディレクトリで実行する。

```bash
npm ls --depth=0 | grep -E 'eslint|typescript-eslint'
npm outdated
```

`npm outdated` の出力では、次の列を確認する。

- `Current`：現在インストールされているバージョン
- `Wanted`：`package.json` のバージョン指定内で更新できるバージョン
- `Latest`：レジストリ上の最新バージョン

`Current` と `Latest` のメジャーバージョンが異なる場合は、更新候補として調査する。最新バージョンが公開されていることだけを理由に、直ちに更新する必要はない。

### 3.2 公式情報を確認する

- [ESLint のサポート状況](https://eslint.org/version-support/)
- [ESLint の移行ガイド](https://eslint.org/docs/latest/use/migrate-to-10.0.0)
- [typescript-eslint のリリース情報](https://typescript-eslint.io/users/releases/)
- [typescript-eslint の依存バージョン対応表](https://typescript-eslint.io/users/dependency-versions/)

次の項目を確認する。

- 現在使用しているバージョンのサポートが継続しているか。
- 新しいメジャーバージョンで重要な不具合やセキュリティ上の問題が修正されているか。
- Node.js、TypeScript、ESLint、typescript-eslint のバージョンに互換性があるか。
- 設定ファイル、ルール、実行方法に変更が必要か。
- 更新によるメリットが、移行にかかる作業量に見合うか。

### 3.3 更新の要否を判断する

- **更新する**：サポート終了、セキュリティ上の懸念、重要な不具合修正などがあり、互換性を確保できる。
- **更新を保留する**：互換性の問題がある、移行作業の準備が必要、現時点で更新のメリットが小さい。
- **継続して確認する**：更新しない場合も、その理由と次回確認事項を記録する。

更新する場合は、通常の更新 PR とは分けて作業ブランチを作成し、移行作業を行う。

なお、移行ガイドは実際に更新するバージョンに対応するものを選ぶ。

## 4. Node.js の月次確認

Node.js は `fnm` で管理しているため、依存パッケージとは別に、Node.js 自体のバージョンとサポート状況を確認する。

### 4.1 現在のバージョンを確認する

プロジェクトのルートディレクトリで実行する。

```bash
fnm current
fnm list
node --version
npm --version
```

次のファイルにバージョン指定がある場合は、併せて確認する。

- `.node-version`
- `.nvmrc`
- `package.json` の `engines.node`

プロジェクトで使用するバージョンと、現在のシェルで有効になっているバージョンが一致しているか確認する。

### 4.2 サポート状況と更新候補を確認する

[Node.js 公式リリース情報](https://nodejs.org/en/about/previous-releases) を確認し、現在使用しているメジャー系列のサポート状況と最新バージョンを把握する。

更新の種類に応じて、次のように判断する。

- **パッチ更新**：セキュリティ修正や不具合修正が含まれることがあるため、サポート対象系列の最新パッチへの更新を原則として検討する。
- **マイナー更新**：リリースノートと互換性を確認し、同じメジャー系列内で更新を検討する。
- **メジャー更新**：サポート期間、Node.js の要件、プロジェクトの互換性を確認し、計画的に移行する。

サポート終了が近い、または既に終了している場合は、別のサポート対象系列への移行を検討する。

### 4.3 更新版をインストールしてテストする

例えば、Node.js 22 系を使用している場合、次のコマンドで 22 系の最新バージョンをインストールできる。

```bash
fnm install 22
fnm use 22
node --version
```

`22` は例である。実際にはサポート状況とプロジェクトの要件に基づいて対象系列を決める。

`fnm install` でインストールしただけでは、使用中のバージョンが切り替わらない場合があるため、`fnm use` と `node --version` で確認する。

更新版に切り替えたら、プロジェクトのルートディレクトリで次を実行する。

```bash
npm ci
npm run lint
npm run typecheck
npm run build
npm run build:extension
npm run test:coverage
```

すべて成功することを確認する。失敗した場合は原因を調査し、解決するまで更新を確定しない。

### 4.4 プロジェクトのバージョン指定を確認する

`.node-version`、`.nvmrc`、`package.json` の `engines.node` などに具体的なバージョン指定がある場合は、更新後のバージョンに合わせる必要があるか確認する。

- 固定バージョンを使用している場合：テスト成功後に指定を更新し、変更をコミットする。
- メジャー系列だけを指定している場合：必ずしもファイル変更は必要ないが、プロジェクトで想定するバージョンと一致することを確認する。
- `engines.node` が指定されている場合：依存パッケージやデプロイ環境の対応バージョンも考慮する。

開発環境だけでなく、Cloudflare Pages のビルド環境でも必要な Node.js バージョンが利用できることを確認する。

## 5. 更新 PR のマージ

マージ前に次の項目を確認する。

- [ ] 更新内容とリリースノートを確認した。
- [ ] メジャー更新の場合、必要な移行作業を確認した。
- [ ] CI がすべて成功している。
- [ ] 変更内容に問題がない。

CI では、少なくとも次の処理が成功していることを確認する。

```bash
npm run lint
npm run typecheck
npm run build
npm run build:extension
npm run test:coverage
```

問題がなければ PR をマージする。CI が失敗した場合は、原因を調査して解決するまでマージを保留する。

## 6. 本番環境の動作確認

Cloudflare Pages へのデプロイが完了したら、主要機能を確認する。

- [ ] ブックマーク一覧が表示される。
- [ ] ブックマークの登録・編集・削除ができる。
- [ ] キーワード一覧が表示される。
- [ ] キーワードの関連付け・解除ができる。
- [ ] ブックマークの外部リンクが開ける。
- [ ] Chrome 拡張機能からブックマークを登録できる。
- [ ] Cloudflare Access の認証を含め、API に正常にアクセスできる。

問題が発生した場合は、影響範囲を確認し、必要に応じて修正やロールバックを検討する。

## 7. 月次作業の記録

作業日、マージした PR、セキュリティアラートの状態、除外対象のメジャー更新、Node.js の更新状況を記録する。

記録例：

| 項目                 | 記録内容                                 |
| -------------------- | ---------------------------------------- |
| 作業日               | YYYY-MM-DD                               |
| マージした PR        | PR 番号と更新内容                        |
| セキュリティアラート | 未解決の有無、対応状況                   |
| ESLint 関連の確認    | 現在のバージョン、最新メジャー、更新要否 |
| Node.js の確認       | 使用バージョン、サポート状況、更新要否   |
| 保留事項             | 保留理由と次回確認事項                   |
| CI・本番確認         | 成功／失敗、問題の有無                   |

## 運用上のルール

- 通常の依存パッケージ更新は月に1回程度まとめて確認する。
- セキュリティアラートは月次作業を待たず、深刻度に応じて早めに対応する。
- ESLint 関連の除外対象メジャー更新は毎月確認し、更新しない場合も理由を記録する。
- Node.js のサポート状況と更新候補を毎月確認する。
- Node.js の更新後は、ローカルのテストと CI の結果を確認する。
- Node.js や ESLint の更新が不要だった場合も空のブランチを無理にマージする必要はない。確認したことと保留理由を記録して Issue をクローズする。
- CI が失敗した PR は、原因を解決するまでマージしない。
- 更新後は、本番環境の主要機能が正常に動作することを確認する。
